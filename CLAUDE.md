# CLAUDE.md — Scientific Knowledge

Handoff guide for managing this project. Read it fully before changing anything.

## 1. What this project is

A personal, offline scientific knowledge base: a reference textbook that grows over years.
The owner is a graduate researcher in computational quantum chemistry. The main interest is
electronic structure theory (Hartree–Fock, correlation methods, density matrices, analytical
gradients, embedding such as DMET, and quantum algorithms such as VQE and SQD).

The owner writes notes in Markdown. `build.py` compiles them, together with the folder tree, into a
single self-contained `index.html` that opens by double-click in any browser: no server, no internet,
no database. Notes are meant to be read, searched, and cross-linked, not tracked as tasks.

Explicit non-goals (the owner decided these): no "currently studying" or "recently updated" panels,
no user accounts, no backend, no cloud sync.

## 2. Layout

```
Scientific_Knowledge/
├── index.html        GENERATED by build.py. Never edit by hand.
├── build.py          notes/ + tree.txt + src/page.html  ->  index.html
├── new_note.py       creates a note from a template (imports read_tree/slug from build.py)
├── tree.txt          THE folder structure and its order (source of truth)
├── notes/            content. Directory path = folder the note is filed in. One .md per note
├── templates/        note.md, paper.md  (placeholders {{id}} {{title}} {{date}})
├── src/page.html     the whole site: HTML + CSS + JavaScript, with a __SITE_DATA__ placeholder
├── vendor/           tex-svg.js (MathJax 3.2.2) + input/tex/extensions/ + fonts/*.woff2
├── README.md         user-facing documentation
├── CLAUDE.md         this file
└── .gitignore        __pycache__/ and *.pyc
```

Dependencies: Python 3.8+ and `pip install markdown` (build only). Viewing needs nothing.

## 3. Commands

```bash
python3 build.py                      # build once; prints counts, warnings, unwritten links
python3 build.py --watch              # rebuild on any change to notes/, tree.txt, src/page.html
python3 new_note.py RHF "Title"       # folder = full tree path or unique last segment
python3 new_note.py Research_Papers "Short title" --kind paper
```

Always run `python3 build.py` after any change and read its output. It must finish without
errors; warnings need a reason to remain (see section 11).

## 4. How the build works

1. `read_tree()` parses `tree.txt` (two-space indent, no tabs) into folder keys such as
   `04_Electronic_Structure_Theory/03_Mean_Field_Theories/01_Hartree_Fock_Theory/RHF`, parents before
   children. `ensure_dirs()` creates the matching directories under `notes/`.
2. Pass 1 walks `notes/**/*.md`. For each file: split front matter, take the folder from its
   directory, take title/id, collect everything. Skipped: any file or folder whose name starts with
   `.` or `_` (use `_draft.md` for drafts). `index.md` is the folder introduction, not a note.
3. Pass 2 renders each body: Markdown to HTML with math protected (section 7), resolves `[[links]]`,
   rewrites relative image/file paths, and resolves `prerequisites`, `related` and `also`.
4. Writes one JSON blob (`folders`, `notes`, `intros`) into `src/page.html` at `__SITE_DATA__`.
   All `<` in the JSON are written as `<`, so note content cannot break out of the script tag.
5. The page's JavaScript builds the sidebar tree, folder pages, note pages, search and the home
   dashboard from that JSON. Nothing is fetched at runtime (`file://` forbids it), which is why all
   data is embedded.

JSON note fields: `id, title, summary, date, status, level, kind, tags[], prereq[], related[],
links[], home, also[], order, cite{authors,journal,year,doi}, mins, html`.
`prereq`/`related` hold note ids, or the raw text of a note that does not exist yet ("planned").

## 5. The folder tree

`tree.txt` is authoritative for folder structure and order. It currently has 10 top-level sections:

```
00_Mathematics                      05_Quantum_Computing
01_Classical_Physics                06_Quantum_Computational_Chemistry
02_Quantum_Mechanics                07_Computational_Methods
03_Quantum_Chemistry                08_Research_and_Literature
04_Electronic_Structure_Theory      09_Reference_Material
```

`04_Electronic_Structure_Theory` (the owner's main area) has 17 children, `00`–`16`: Foundations of
Quantum Chemistry; Mathematical and Computational Foundations; Basis Sets and Orbital Theory;
Mean Field Theories; Electron Correlation and Wavefunction Methods; Multireference Electronic
Structure; Reduced Density Matrices; Analytical Derivatives and Response Theory; Electronic and
Molecular Properties; Excited State and Nonadiabatic Theory; Quantum Embedding; Quantum Algorithms;
Stochastic and Tensor Network Methods; Integral and Algorithmic Techniques; Software and
Implementations; Benchmarking and Validation; Applications and Literature.
Embedding and Quantum Algorithms are deliberately separate folders (10 and 11).

`09_Reference_Material` holds notation, units and constants, mathematical identities, and
convention comparisons (for example chemist vs physicist integral notation, RDM normalisations).

Rules:
- Leading digits (`04_`) become the displayed folder number and fix the order. Unnumbered names
  keep the order written in `tree.txt`, not alphabetical.
- Display names come from folder names: `_` becomes a space, the number prefix is stripped, and a
  small `FIX` list in `src/page.html` improves a few (Schrodinger to Schrödinger, `Hartree Fock` to
  Hartree–Fock, `CCSD T` to CCSD(T), and so on). Add entries there when a name displays badly.
- The owner may flatten folders (for example, Basis Sets and Orbital Theory is intended to hold only
  notes, no subfolders). Do it by deleting the child lines from `tree.txt` and rebuilding.
- Folder names must contain only letters, digits and underscores (they are used in URL hashes).
- Git does not track empty directories; `build.py` recreates them from `tree.txt`.

## 5b. Routes (URL hash)

`#` empty = home. `#<folder path with / replaced by ~>` = folder. `#n.<note id>` = note.
`#k.<kind>` = notes of one kind. Hash tokens are limited to letters, digits and `. _ ~ -`, so note ids
and folder names must stay within that set. Ids are normalised to lowercase hyphenated slugs.

## 6. Note format

File: `notes/<folder path>/<name>.md`. The folder is where the file sits.

```markdown
---
id: rhf
title: Restricted Hartree–Fock
summary: One or two sentences for lists and search.
status: in-progress        # not-started | in-progress | complete | needs-revision
kind: theory               # theory | derivation | algorithm | implementation | comparison | paper | reference
level: intermediate        # introductory | intermediate | advanced
tags: [SCF, mean field]
prerequisites: [variational-principle, second-quantization]
related: [uhf]
also: [03_Quantum_Chemistry/04_Molecular_Orbital_Theory]
order: 1                   # optional; default alphabetical by title
date: 2026-10-31
---
```

- Front matter is a small YAML subset parsed by hand: `key: value`, `key: [a, b]`, or `key:` followed
  by `- item` lines. Comment lines start with `#` and must be on their own line. Unknown keys are
  ignored. There is no PyYAML dependency; do not introduce one.
- `id` defaults to the slugified file name (leading `01_` style numbers stripped). **Never change an
  id once any note links to it.** Duplicate ids get a numeric suffix and a warning.
- `title` defaults to the first `# Heading` in the body (which is then removed from the body), else
  the file name. The body should start at `##`; the page already renders the title.
- A paper note adds `authors`, `journal`, `year`, `doi` (rendered as a citation line).
- `index.md` in a folder: that folder's introduction, shown above its lists. Front matter ignored.
- Unrecognised `status` values are accepted but produce a warning.

### Links

- `prerequisites` (shown at the top of a note) and `related` (shown below), by id or title.
- In text: `[[id or title]]` or `[[id|label]]`. Resolution tries id, then slugified title, then
  slugified file stem. Prefer ids.
- The page derives **Required by** (notes listing this one as a prerequisite) and **Mentioned in**
  (notes that relate to or link to it). Do not maintain these by hand.
- A reference to a note that does not exist is not an error: it renders greyed out as "planned" and
  `build.py` lists it. When the note is later created, matching ids/titles turn into real links.

### Notes in two folders

One note has one home (its directory). `also: [folder/path, ...]` lists it in other folders too, shown
there as "Shortcut" with its home path. No duplicated content. Use it sparingly: if a note is only
*connected* to another area, use `related` or `[[ ]]`. Choose the home by the most specific
fitting folder. When a subject recurs in several top-level sections of the tree (VQE, embedding,
potential energy surfaces, symmetry), split by role (theory in one home, software details in the
software folder) and link them. Never copy a note into two files.

## 7. Markdown and math rules (build.py `Renderer`)

Order of operations: stash code, stash math, escape stray `$`, resolve `[[links]]`, restore code, run
python-markdown (extensions: tables, fenced_code, admonition, sane_lists, md_in_html), tidy HTML,
restore math. Consequences:

- Math: `$...$` inline, `$$...$$` display (own lines preferred), also `\(...\)` and `\[...\]`.
  Underscores, stars and `<` inside math are safe. Display math is wrapped as `<div class="eq">`.
- Inside table cells write `|` normally in math (`$\langle a|b\rangle$`); `\|` would mean the double bar.
- A `$` that is not math (prices, shell prompts) is escaped to `\$` so MathJax shows a plain dollar.
  Code spans and fenced blocks are never touched.
- Admonitions need a blank line before and four-space indentation: `!!! example "Worked example"`.
  Types: example, note, warning. Styling: `.admonition` in `src/page.html`.
- Images and file links (`pdf png jpg svg gif txt csv py ipynb zip json ...`) with relative paths are
  rewritten to `notes/<note dir>/<path>`, so place assets next to the note and keep `notes/` beside
  `index.html`.
- Footnotes are not enabled on purpose (their `#fn:` anchors collide with hash routing).
- Tables are wrapped in a scroll container. Long inline formulas scroll inside their paragraph; prefer
  display equations for long expressions.
- Heading anchors for the side contents list are assigned in JS (`h2` only).

## 8. The page (`src/page.html`)

One file: `<style>`, markup, a JSON data script (`id="site-data"`), the MathJax config, then the app
script. Design: IBM Plex Sans Condensed (display), Literata (body), IBM Plex Mono (labels); teal
accent; light/dark by tokens defined on `:root` with a `data-theme` override. Fonts and colours are
the CSS variables at the top. The masthead says "Theory Notebook", the home title is `SITE` in the
script ("Scientific Knowledge").

Structure of the script: build the tree from `DATA.folders`; attach notes (`n.node` home,
`n.alsoNodes` shortcuts); compute counts and reverse links; routes `resolve()/go()/setRoute()`; draw
functions `drawHome`, `drawFolder`, `drawNote`, `drawKind`, `drawResults`; sidebar with collapsible tree
and a phone drawer; search (case-insensitive, all words must appear, over title, summary, tags, kind,
full text and folder names; no ranking); theme toggle (localStorage, wrapped in try/catch).

Constraints when editing the page:
- **Stay offline.** No CDN, no web fonts, no `fetch`. Fonts are `@font-face` rules pointing to
  `vendor/fonts/` (kept between the `/*@offline-fonts*/` markers). MathJax loads from
  `vendor/tex-svg.js`; `vendor/input/tex/extensions/` must stay because MathJax lazy-loads extensions
  such as `\boldsymbol` from there. If a LaTeX macro fails offline, check that extension exists.
- Keep both themes working (every colour is a token); keep it usable at 390 px width with no
  horizontal page scroll; keep keyboard focus visible and respect reduced motion.
- Do not break `__SITE_DATA__`; `build.py` exits with an error if it is missing.
- MathJax can finish loading before or after the page script runs; `typeset()` handles both
  (pending target). Keep that logic if you refactor.

## 9. Common tasks (playbook)

| Task | Steps |
|---|---|
| Add a note | `new_note.py`, write content, `build.py`. Set `summary`, `kind`, `status`, `prerequisites`. |
| Add a folder | Add a line in `tree.txt` at the right indent and position; `build.py`. |
| Flatten or delete folders | Delete the lines in `tree.txt`. First move any notes up; fix `also:` entries that name the removed folders. Remove leftover empty dirs with `rmdir`. |
| Rename a folder | Change it in `tree.txt` and rename the directory under `notes/` (use `git mv`). Update `also:` entries naming it. |
| Move a note | Move the file to the new directory. Its id and links are unaffected. |
| Rename a note id | Avoid. If required: update the `id`, then grep all notes for the old id in `prerequisites`, `related`, `[[...]]`, and `#n.` links. |
| Add a `kind` or `status` value | Kinds are open-ended (any slug works; add a display name in `KIND`/`KINDS` in the page script). Statuses are fixed in `STATUSES` (build.py) and `STATUS` (page). |
| Change look and feel | Edit tokens and CSS in `src/page.html`, rebuild, check light, dark and phone widths. |
| Fix a display name | Add a pair to `FIX` in the page script. |
| Add a new metadata field | Parse it in `build.py` pass 2, add it to the JSON, render it in `drawNote`, document it in `README.md`. |

## 10. Standards for note content

These matter more than any code. The notes are a reference the owner will trust.

- **Correctness first.** Every equation, sign, prefactor and numerical value must be checked. Verify
  numerical examples by running code (Python with NumPy/SciPy, or PySCF when available) rather than
  recalling values. State the conventions used (spin-orbital vs spatial orbital, chemist's vs physicist's
  integral notation, normalisation of RDMs, units). If unsure of a result, say so in the note instead
  of guessing.
- **Style the owner wants:** rigorous derivations with explicit equations, every symbol defined before use,
  assumptions stated, and a worked numerical example on a small system. Write at graduate level; do not
  pad with generic explanation.
- **Sources.** Cite textbooks (chapter/section) and papers (authors, journal, year, DOI). Never invent a
  reference, DOI, page number or quotation. If a citation cannot be verified, leave a note marked
  "to verify".
- **Own words.** Do not paste textbook passages or figures; derive and explain in original wording.
  Unpublished results from the owner's lab must not be added unless the owner says so.
- **One concept per note**, short and linkable, rather than long surveys. Use `prerequisites` and `related`
  honestly; add `status: needs-revision` when a note is known to be incomplete or uncertain.
- Follow `templates/note.md` section order where relevant; delete sections that do not apply.

## 11. Definition of done for any change

1. `python3 build.py` runs without errors.
2. Its warnings are understood. Expected: "linked note(s) not written yet" for planned links.
   Not acceptable: duplicate ids, folders missing from `tree.txt` (unless intentional), unknown status.
3. Open `index.html` in a browser (or a headless one) and check the affected pages: equations
   typeset, no console errors, links resolve, shortcut/also lists correct, and the sidebar counts are right.
4. For page changes also check dark mode and a 390 px wide viewport.
5. If Playwright is available, a useful smoke test: load `file:///.../index.html` with all network
   requests aborted, open a note, and assert `mjx-container` elements exist, there are no page errors,
   and `document.documentElement.scrollWidth - clientWidth` is 0 at 390 px.
6. Commit with a short message naming what changed (for example `Add RHF note`, `Flatten basis-set folder`).

## 12. Git

Track everything except caches. `index.html` is generated but stays tracked so a fresh clone works.
Commit notes and `tree.txt` changes separately from `src/page.html` or `build.py` changes. Do not commit
virtual environments. When folders are renamed, use `git mv` so history follows.

## 13. Known limitations and ideas (not yet done)

- No code syntax highlighting (code blocks are styled, monochrome).
- No dependency graph or prerequisite-chain view; only direct lists.
- The side contents list appears only on viewports 1400 px and wider.
- Search is a plain all-words match, unranked.
- `index.html` embeds every note. Fine for hundreds of notes; for thousands, move the JSON into a separate
  `.js` file loaded by a `<script src>` tag (this works on `file://`, unlike `fetch`).
- Footnotes unsupported (hash-routing conflict).
- Folder introduction pages (`index.md`) ignore front matter.

## 14. Things to ask the owner before doing

- Changing the top-level sections or renumbering existing folders (notes link by folder path in
  `also:`, and numbers are part of the owner's mental map).
- Deleting any note, or restructuring existing notes in bulk.
- Adding dependencies, a server, a database, or any network access at runtime.
- Adding features the owner has declined (section 1).
